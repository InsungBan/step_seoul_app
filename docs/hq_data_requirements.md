# 본사 UI 데이터 요구사항 — 첨부 UI 기준

첨부된 대시보드·최종결재함·주문/배송/수령/반품·재고/상세·품의/작성·발주/상세·판매·기준정보 화면을 바탕으로 구성했습니다.
`db/schema.json`에 실제 존재하는 필드와 FK 관계만 사용합니다. 업무 정의에 등장하더라도 스키마에 없는 정보는 해당 셀·카드·패널에 **데이터가 없습니다.**를 표시합니다.

## 추가 DB 데이터 또는 관계가 필요한 항목

| 화면 | 필요한 정보 | 현재 DB의 제약 |
| --- | --- | --- |
| 공통 로그인·권한·알림 | 로그인 직원, 세션, 역할/권한, 알림 내용·읽음 상태·발생 시각 | 직원 목록만으로 현재 사용자 또는 이사 권한을 판정할 수 없음 |
| 신발 상품·카테고리 차트 | 상품 이미지 URL, 사이즈, 색상, 성별, 상품 유형/카테고리, 판매 상태 | `shoe`에는 ID·상품명·가격·기준재고·현재재고만 있음 |
| 주문 목록·상세 | 주문 생성일, 주문 상태, 결제수단, 주문 목적 대리점, 주소 | 구매일 대신 연결된 결제일을 **결제일자**로 표시. 대리점은 결제 ID+고객 ID로 유일한 수령 기록이 있을 때만 연결 |
| 배송 목록·진행 상태 | 주문/결제 ID 연결, 발송일, 도착일, 예상 도착일, 운송장, 배송업체, 출발지, 단계별 이력 | `shipment`는 상품·직원·대리점·수량·배송상태만 가지고 있음. 같은 상품이라는 이유로 특정 주문 배송으로 연결하지 않음 |
| 수령·인증 상세 | 주문 상품 단위 연결, 도착일, 인증 방법·성공/실패 결과, 확인 시각 | `receive`는 결제 연결·수령일·상태가 있음. 인증 코드는 민감 필드라 HQ snapshot에서 제외하며 화면에는 없는 상태로 표시 |
| 반품·검수·환불 | 반품과 구매·고객·대리점 연결, 반품 사유/수량/상태, 검수 결과, 반품→회수→환불 FK 연결, 환불 상태/일자 | `return_record`에는 상품·직원·반품일만 있음. 회수·환불은 개별 목록으로 표시하며 고객만 같다고 연결하지 않음 |
| 대리점별 재고 | 대리점/창고 ID + 상품 ID + 수량 + 기준재고 + 갱신일 | 상품 전체 재고를 대리점 재고로 분배할 근거 없음 |
| 재고 변동 이력·30일 재고 추이 | 원장 ID, 상품/위치, 발생 시각, 증감, 사유, 변동 후 재고, 원본 거래 | 현재 재고 값 하나로 과거 추이를 복원할 수 없음 |
| 재주문·자동 발주 | 임계치 설정, 자동발주 대상 플래그, 생성 원인, 생성일, 자동 생성 여부/처리 결과 | 30% 미만 경고는 UI 계산 가능하지만 자동발주 설정이나 생성 이력은 없음 |
| 품의 목록·작성·최종결재 | 작성자 FK, 생성일, 유형, 긴급도, 요청 부서/대리점, 요청 상품·수량·금액, 희망일, 명시적 결재 단계/담당자, 첨부파일 | `approval`는 제목·내용뿐. `approval_process`의 직원은 **결재 담당 직원**으로 표시하며 작성자라고 가정하지 않음 |
| 발주→수주→입고 상세 | 발주와 수주 직접 FK, 발주 상태, 제조사 접수/출고일, 입고 예정일/실제 입고일, 검수 결과/담당자, 지연 사유 | 같은 상품·제조사라는 이유로 특정 발주와 수주를 연결하지 않음. 수주 완료를 입고 완료로 가정하지 않음 |
| 제조사 연락처·납품 첨부 문서 | 담당자, 전화, 이메일, 업무시간, 문서 URL·등록일·등록 직원 | 제조사는 ID·이름만 있음 |
| 대리점별 판매·반품률 | 주문/결제와 판매 대리점의 직접 연결, 환불·반품 대상 거래와 수량, 취소 상태 | 수령 대리점을 판매 대리점으로 가정하거나 반품 행 수로 판매 수량 대비 반품률을 계산하지 않음 |
| 기준정보 보조 정보 | 고객 활성 여부, 직원 재직 상태, 대리점 담당자/영업 상태/수정일, 제조사 국가 | 총 등록 건수만 표시하고 존재하지 않는 상태별 수치는 표시하지 않음 |

## 기존 DB로 연결한 정보

- `/hq/snapshot`: 실제 테이블을 읽는 공통 조회 API. 기존 14개 목록에 제조·회수·환불·인증·장바구니 목록 추가. 비밀번호·인증 코드·환불 카드번호는 제외.
- 오늘/월간/최근 7일/선택 기간 매출과 일별 차트: `payment_status=1`, `payment_date`, `payment_amount`. 행이 없는 기간에는 빈 상태 표시.
- 판매 순위: 결제 완료 기록과 연결된 `purchase`의 상품별 수량 합계. 매출은 구매 당시 단가×수량으로 계산.
- 재고 비율과 상태 분포: 현재재고÷기준재고. 기준재고가 없거나 0이면 비율은 빈 상태. 분포는 유효 비율을 가진 **상품 수** 기준.
- 제조사 이름: `manufacturing` 관계로 연결. 여러 제조사는 모두 표시.
- 품의 상태: `approval_process`의 실제 상태. 여러 기록이면 처리일(없으면 결재일)이 가장 최근인 기록. 동률/날짜 누락으로 최신 기록을 정할 수 없으면 빈 상태.
- 지역별 대리점 수: `store.district_name` 집계. 제조사별 발주 금액: `purchase_order.get_amount` 집계.
- 오늘 대리점별 수령 건수: 수령 완료 상태와 수령일을 기준으로 집계.
- 품의 작성: 기존 `POST /approval/upload`로 제목·사유만 저장. 상품 요청 명세·결재 라인·첨부파일은 저장할 스키마가 없으므로 제공하지 않음.

## 추가 API 후보

필요한 DB 관계가 준비된 후 다음 조회 API를 추가할 수 있습니다. 현재 구현된 엔드포인트를 뜻하지 않습니다.

- `GET /hq/orders/{id}/tracking`: 주문별 배송·인증·수령·반품 전체 이력
- `GET /hq/inventory/by-store`, `GET /hq/inventory/movements`: 위치별 재고 및 재고 원장
- `GET /hq/sales/by-category`, `GET /hq/sales/by-store`: 카테고리·대리점별 매출
- `POST /hq/proposals/submit`: 품의 명세와 결재 라인을 한 트랜잭션으로 생성
- `POST /hq/approvals/{id}/decision`: 권한 확인 후 승인/반려, 자동 발주와 중복 방지
- `GET /hq/purchase-orders/{id}/progress`: 발주별 수주·출고·입고·검수·첨부 문서

DB 테이블 또는 필드는 변경하지 않았습니다. 결재·출고·수령·환불·자동발주 등 업무 상태를 바꾸는 처리는 권한과 관계가 준비되기 전까지 임의로 실행하지 않습니다.
